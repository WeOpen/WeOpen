# 个人管理平台产品需求文档

版本：v0.1  
日期：2026-05-13  
状态：草案  
项目代号：WeOpen Personal Platform

## 1. 背景

个人开发者经常把博客、域名、云存储、常用开发工具、代码片段、书签、笔记和项目事项分散在不同服务中管理。信息分散带来三个问题：

- 入口分散：常用工具、资源和配置需要在多个网站之间切换。
- 数据分散：博客内容、文件、域名、证书、订阅和提醒没有统一视图。
- 扩展困难：每新增一个个人工具都要重新做登录、菜单、设置、存储和部署。

本项目目标是建设一个可免费或低成本部署的个人管理平台。平台以插件机制承载功能，先满足个人自用，再逐步扩展为可分享、可部署、可二次开发的个人效率系统。

## 2. 产品定位

### 2.1 一句话定位

一个面向个人开发者的插件化管理平台，用统一后台管理博客、开发工具、域名、云存储和个人数据。

### 2.2 目标用户

- 个人开发者：有个人博客、域名、GitHub、云存储和常用开发工具。
- 独立开发者：需要管理多个项目、域名、部署、文档和资源。
- 技术博主：需要写作、发布、归档、SEO、素材管理和数据统计。
- 自托管爱好者：希望低成本掌控个人数据，但没有固定服务器。

### 2.3 核心价值

- 统一入口：一个 Dashboard 聚合个人资源、工具、提醒和状态。
- 插件扩展：博客、工具箱、域名、存储等功能按插件接入。
- 低成本部署：优先使用 Vercel 免费层、Cloudflare R2 和托管数据库。
- 多端复用：Web 端用于在线访问，桌面端用于本地快捷工具和离线能力。
- 可迁移：数据结构、文件和配置避免被单一平台锁死。

## 3. 设计约束

### 3.1 部署约束

- 用户没有服务器，v1 优先使用 Vercel 免费部署。
- 后端使用 Go 提供 API，但要适配 serverless 无状态运行方式。
- 前端使用 Next.js。
- 桌面端使用 Wails v3，并复用尽量多的 Go 和 React 能力。
- 对象存储优先使用 Cloudflare R2 免费层。
- 不依赖常驻后台进程，不默认使用需要自建服务器的队列、WebSocket 服务或长任务服务。

### 3.2 平台约束

- Vercel Go Runtime 目前适合轻量 API，但不适合长时间运行任务。
- Vercel Services 是更理想的前后端组合方式，但当前仍需要按可用性评估；v1 设计应支持“两项目部署”的保守路线。
- Wails v3 仍处于较早阶段，桌面端 v1 以个人使用、验证体验为主。
- R2 适合文件、图片、备份和对象存储，不应被当成关系数据库使用。

### 3.3 产品约束

- v1 只做单用户或邀请制，不做开放注册和多租户。
- v1 不做插件市场，不支持第三方在线安装任意插件。
- v1 不做复杂权限系统，采用“单用户 + 插件权限声明 + 高风险操作确认”。
- v1 不做移动 App，先保证 Web 和桌面端。

## 4. 产品目标

### 4.1 v1 目标

- 建立平台底座：登录、Dashboard、插件注册、设置、存储、基础审计。
- 完成 4 个核心插件：博客管理、程序员工具、域名管理、R2 云存储。
- 提供可部署的 Web 版本。
- 提供可运行的桌面端原型，复用核心 UI 和部分 Go 能力。
- 提供明确的插件开发规范。

### 4.2 成功指标

- 用户可以在 30 分钟内完成本地启动和 Vercel 部署。
- 用户可以通过 Dashboard 进入所有已启用插件。
- 博客插件可以完成文章从草稿到发布的完整流程。
- R2 插件可以完成上传、浏览、下载、删除和公开链接管理。
- 域名插件可以展示域名、DNS、证书和到期提醒。
- 程序员工具插件提供至少 10 个高频工具。
- 新增一个内部插件不需要改动平台核心路由以外的通用逻辑。

## 5. 非目标

v1 明确不做：

- 公开 SaaS 化运营。
- 多组织、多租户、团队协作。
- 在线插件市场和远程动态代码加载。
- 全功能 CMS 前台主题系统。
- 大文件网盘级同步客户端。
- 复杂工作流引擎。
- 支付、订阅、商业化能力。
- 高并发公开 API 服务。

## 6. 用户场景

### 6.1 每日入口

用户打开平台后，在 Dashboard 看到：

- 最近文章草稿和待发布文章。
- 域名到期、SSL 到期、DNS 异常提醒。
- R2 存储容量、最近上传文件和公开文件数量。
- 常用开发工具快捷入口。
- 最近操作记录。

### 6.2 写博客

用户进入博客插件，创建 Markdown 文章，上传封面到 R2，设置标签、分类、摘要、SEO 信息，保存草稿，预览后发布。

### 6.3 使用开发工具

用户进入工具箱，快速进行 JSON 格式化、JWT 解码、Base64、哈希、时间戳、Cron 表达式、UUID、正则测试、颜色转换等操作。工具尽量本地运行，不把敏感内容发送到服务端。

### 6.4 管理域名

用户绑定 Cloudflare API Token 后，平台读取域名列表、DNS 记录、证书状态和到期时间。v1 以只读和提醒为主，写操作需要二次确认和审计记录。

### 6.5 管理云存储

用户配置 R2 Bucket 后，可以上传博客素材、附件和备份文件。平台支持私有文件、公开文件、预签名下载链接和对象元信息查看。

### 6.6 桌面快捷工具

用户打开桌面端，使用本地开发工具、查看最近文章、上传文件、管理常用链接。桌面端可连接远程 API，也可在后续版本提供本地模式。

## 9. 权限与安全需求

### 9.1 账号安全

- v1 支持单用户账号。
- 密码必须哈希存储。
- Session 需要过期时间。
- 支持修改密码。
- 登录失败需要限流或冷却。

### 9.2 密钥安全

- Cloudflare、R2、Vercel 等 Token 服务端加密存储。
- 前端不直接暴露 Secret。
- 配置页只展示脱敏后的密钥。
- 删除、替换密钥需要记录审计。

### 9.3 插件权限

每个插件必须声明权限，例如：

- `storage:read`
- `storage:write`
- `domain:read`
- `domain:write`
- `blog:write`
- `secret:read`
- `task:schedule`

平台根据权限决定是否允许调用对应能力。v1 权限主要用于约束插件和展示风险，不做多用户授权。

### 9.4 高风险操作

以下操作需要二次确认：

- 删除文件。
- 删除文章。
- 修改 DNS。
- 删除 DNS。
- 替换 API Token。
- 执行批量操作。
- 导出全部数据。

## 10. 数据需求

核心实体：

- User：用户账号。
- Session：登录会话。
- Plugin：插件注册信息、启用状态、版本。
- PluginSetting：插件配置。
- Secret：外部服务密钥。
- AuditLog：审计日志。
- Notification：提醒。
- BlogPost：文章。
- BlogTaxonomy：分类和标签。
- DomainAsset：域名资产。
- DnsRecordSnapshot：DNS 快照。
- StorageObjectIndex：R2 对象索引。

数据设计原则：

- 业务数据存关系数据库。
- 文件内容和二进制对象存 R2。
- 插件配置使用结构化 JSON，但关键查询字段要独立列。
- 外部服务读取结果可以缓存，但不要把缓存当作唯一事实来源。

## 11. API 需求

API 分为平台 API 和插件 API。

平台 API 示例：

- `POST /api/auth/login`
- `POST /api/auth/logout`
- `GET /api/me`
- `GET /api/dashboard`
- `GET /api/plugins`
- `PATCH /api/plugins/{id}`
- `GET /api/settings`
- `PATCH /api/settings`
- `GET /api/audit-logs`

插件 API 示例：

- `GET /api/plugins/blog/posts`
- `POST /api/plugins/blog/posts`
- `GET /api/plugins/devtools/tools`
- `GET /api/plugins/domains/assets`
- `GET /api/plugins/storage/objects`
- `POST /api/plugins/storage/upload-url`

API 设计原则：

- 使用 JSON。
- 错误返回统一结构。
- 支持请求 ID。
- 写操作记录审计。
- 对插件 API 做命名空间隔离。
- 使用 OpenAPI 生成前端 SDK。

## 12. 交互需求

### 12.1 Dashboard

- 左侧为主导航。
- 顶部提供全局搜索、用户菜单、同步状态。
- 主区展示插件卡片和提醒。
- 卡片必须可点击进入插件详情。

### 12.2 插件页

- 每个插件保持统一布局。
- 插件内部可以定义自己的列表、表单和工具视图。
- 插件设置入口统一放在设置中心和插件详情页。

### 12.3 表单体验

- 保存状态明确。
- 高风险操作弹出确认。
- 外部 API 调用失败需要展示可理解的错误。
- Token、Secret、Endpoint 输入需要校验格式。

### 12.4 桌面端体验

- 桌面端默认提供快速入口和常用工具。
- 用户可以配置连接远程 Web API。
- 桌面端敏感本地数据应存系统安全存储或加密文件。

## 14. 验收标准

v1 总体验收：

- 平台可以本地启动、登录、进入 Dashboard。
- 至少 4 个核心插件可启用。
- 插件菜单、权限、设置、API 命名空间完整。
- 博客和 R2 能形成闭环。
- 域名插件至少支持只读管理和提醒。
- 桌面端能复用基础 UI，并提供至少工具箱能力。
- 敏感配置不会出现在前端 bundle、日志或公开响应中。
- 基础测试、类型检查、构建通过。

## 15. 风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| Vercel Go Runtime 能力限制 | API 部署不稳定或能力不足 | 保留独立 API 项目和 Cloudflare Workers/Fly.io 迁移路线 |
| Wails v3 仍不够稳定 | 桌面端开发风险 | v1 桌面端只做轻量原型，核心能力先在 Web/API 成熟 |
| 插件系统过度设计 | 拖慢 v1 | 采用编译期插件，不做远程动态安装 |
| 免费层限制 | 调用、带宽、存储受限 | 默认单用户低频场景，加入用量面板 |
| 密钥泄露 | 高危安全问题 | 服务端加密、脱敏展示、审计、最小权限 Token |
| 域名/DNS 写操作误操作 | 影响线上站点 | v1 只读优先，写操作延后并加入强确认 |

## 16. 待确认问题

- v1 是否只支持单用户，还是要预留邀请制多用户？
- 博客是否需要公开前台，还是只做管理后台和 API？
- 域名管理优先支持 Cloudflare，是否还要支持 Vercel Domains？
- 数据库优先选择 Postgres、SQLite/libSQL 还是 Supabase？
- 桌面端 v1 是连接远程 API，还是需要本地独立运行模式？
